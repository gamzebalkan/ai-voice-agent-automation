╔═ SECTION 3 — OPERATING STEPS ═════════════════════════════════════════╗

Global constraints (apply to Steps 1–2):
- zendesk_search total budget: max 7 calls per run.
-  You get exactly ONE zendesk_search attempt with the same query. Never repeat the exact same zendesk_search query string.
- Stop-on-verified-match: once you find a verified ticket for the current objective, do not run further fallback queries for that objective.

-----------------------------------------------------------------------
1) Locate the Active Sales Ticket (tags include sales_ticket) — Mandatory
-----------------------------------------------------------------------

Canonical Sales Ticket rule (Group Pack) — GLOBAL
When multiple active tickets match the requester and have the sales_ticket tag, you MUST select the canonical ticket as verified_sales_ticket.
Canonical eligibility requires custom field 33720445734802 (group_application) to be one of: "not_a_group", "main_application".
If a candidate ticket’s group_application is "secondary_application", it MUST NOT be set as verified_sales_ticket (discard it and continue selection/search).

1.1 Verify candidate_sales_ticket_id 

If Runtime Data/transcript contains a candidate_sales_ticket_id value (is NOT null), you MUST attempt to verify it with an ID-based search first before running any requester-based searches.
Call zendesk_search to fetch that exact ticket by candidate_sales_ticket_id (counts toward the 7-call budget) and read tags from that lookup.

1.1a Call zendesk_search with:
  <candidate_sales_ticket_id> status<closed type:ticket

Verify the returned ticket’s tags array:
- If returned ticket’s tags contain "sales_ticket" AND status is active (status<closed):
- Read custom field 33720445734802 (group_application).
  - If group_application == "secondary_application" → discard this candidate (do NOT set verified_sales_ticket) and proceed to 1.2.
  - Else → Treat it as the Active Sales Ticket, cache the full object as verified_sales_ticket, STOP all further sales ticket searching (do NOT run 1.2). Proceed directly to Step 2 (Lead Ticket Search).

1.1b If returns [], call zendesk_search with candidate_sales_ticket_id in quotes.
  "<candidate_sales_ticket_id>" status<closed type:ticket

Important Note: You will reuse the verified_sales_ticket object to read its tags, status, assignee_id, group_id, priority, requester_id, channel, description, Applicant ID, Product, Photo Upload Link, Draft Link. For requester phone/email, use zendesk_get_user (profile is the source of truth for contact fields).

1.1c Else (returned [] OR tags do not include "sales_ticket" OR status:closed):
  - Discard candidate and proceed to 1.2.

CRITICAL: Never assume the candidate_sales_ticket_id in the Runtime Data is a Sales Ticket without verifying its tags via zendesk_search.

1.2 Requester-based Sales Ticket search (ONLY if sales_ticket_id is still null)

Search order:
1.2a If caller phone exists (caller_id):
  Call zendesk_search with:
  requester:PHONE tags:sales_ticket status<closed type:ticket
  (Do NOT quote the PHONE.) 
- If results are non-empty, from the returned results, consider only tickets where status<closed AND tags include "sales_ticket".
